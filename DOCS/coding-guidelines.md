# コーディング規約

## 言語

- アプリケーションコードは TypeScript で書きます。
- TypeScript の `strict` 設定を維持します。
- モジュール境界、公開 helper、複雑なデータ構造では型を明示します。
- 可読性が上がる場合は、プロジェクト内 import に `@/*` のパスエイリアスを使います。

## React Native

- 関数コンポーネントと hooks を基本にします。
- 画面固有の振る舞いは route file に置きます。
- 再利用する UI は `components/` に移します。
- 再利用する非UIロジックは `utils/` または機能単位の module に移します。
- プラットフォーム機能は、可能な限り Expo modules または実績のある React Native ライブラリから利用します。

## 状態

グローバル状態管理ライブラリが決まるまでは、以下を基本にします。

- 画面内の一時的な操作状態には local state を使います。
- 適切な場合は、ナビゲーション状態を route / URL で表現します。
- 一時的な UI 都合だけでアプリ全体の状態管理を導入しません。

## エラーハンドリング

- ユーザーが対応できるエラーは UI に表示します。
- 技術的な詳細ログは、デバッグに役立つ場合だけ残します。
- カメラ、マイク、音声認識、メディアライブラリ、ストレージ、将来のクラウド同期では、権限エラーを明確に扱います。

## テストと確認

テスト方針はまだ確定していません。

AI によるコード変更では、当面以下を最低限の期待値とします。

- TypeScript / React Native ファイルを変更した場合は、可能な限り lint を実行します。
- `npm run lint` はセットアップ手順ではなく、コード変更後や完了報告前の確認として実行します。
- 自動化できない確認は、何を確認したかを報告します。
- 安定したビジネスロジックができたら、そこから重点的にテストを追加します。

## 文字コード

- ソースコードと Markdown は UTF-8 BOMなしで保存します。
- 文字化けした日本語を新しいコードへコピーしません。
- 文字化けは、元の意図を確認した上で根本から修正します。
