# 保存設計と実現可能性

## 結論

MVP は実現可能です。

ただし、iOS と Android では写真ライブラリやメディア管理の仕組みが異なるため、カメラ、音声認識、写真保存、アルバム復元は両方の実機で確認します。

特に確認が必要な領域:

- 音声認識が継続的に安定するか。
- 「シャッター」の認識精度が十分か。
- 外側カメラから内側カメラへの切り替え時間。
- 切り替え直後の内側写真が暗い、ぼける、古いフレームになる問題がないか。
- 端末の写真アプリに保存した画像を、後からアプリ内アルバムで確実に再取得できるか。
- iOS / Android の権限ダイアログが、撮影体験を大きく壊さないか。

## 開発方式

このプロジェクトは Expo / React Native で開発します。

基本的には TypeScript / React の共通コードを書き、Expo modules や React Native ライブラリが iOS / Android のネイティブ機能を呼び出します。

```text
React Native / TypeScript のアプリコード
  -> Expo module / React Native library
    -> iOS のネイティブAPI
    -> Android のネイティブAPI
```

OSごとの分岐が必要な場合は、`Platform.OS` またはプラットフォーム別ファイルを使います。

```text
photoStorage.ios.ts
photoStorage.android.ts
```

共通コードだけで進められる領域もありますが、保存や権限のようにOS差が出る領域は、早い段階で抽象化します。

## 既存の土台

現在のプロジェクトには、MVP に必要な主要依存関係がすでに入っています。

- `expo-camera`
- `expo-media-library`
- `expo-speech-recognition`
- `@shopify/react-native-skia`
- `expo-file-system`
- `expo-sqlite`
- `expo-router`
- `expo-dev-client`

現在の土台で進めやすいもの:

- カメラ画面のUI整理
- 音声認識による撮影開始
- 外側カメラから内側カメラへの連続撮影
- Skia による合成画像生成
- 合成後プレビュー

設計を固めてから実装したいもの:

- 写真セットの永続管理
- アプリ内アルバム
- 合成パターン選択の保存
- 写真アプリ保存とアプリ内管理の両立

## 推奨する保存方式

MVP では、軽量なローカルDBとして `expo-sqlite` を使います。

ここでのDBはサーバーDBではありません。端末内で写真セットの紐付けを管理するための小さなローカルDBです。

画像本体はアプリ内ファイルとして保存し、DBには紐付け情報を保存します。成果物画像だけは、ユーザーが通常の写真として扱えるように端末の写真アプリにも保存します。前後カメラ撮影では合成後写真、背面カメラのみ撮影では背面写真が成果物画像です。

MVP で保存する `PhotoSet`:

```text
id
createdAt
captureMode
orientation
backLocalUri
frontLocalUri
composedLocalUri
composedAssetId
pattern
composedWidth
composedHeight
frontImageFocusX
frontImageFocusY
frontImageScale
deletedAt
```

`id` は撮影結果を1セットとして束ねる識別子です。前後カメラ撮影では外側写真、内側写真、合成後写真を束ね、背面カメラのみ撮影では背面写真1枚を束ねます。`id` には時刻由来の文字列を含めますが、アルバムの日付順や日付グルーピングでは `createdAt` を正本として使います。

各項目の意味:

- `captureMode`: `dual` または `backOnly`。前後カメラ撮影か、背面カメラのみ撮影かを表す。
- `orientation`: `portrait` または `landscape`。カメラが通知する撮影時の向きを優先し、取得できない場合は背面カメラ撮影結果の `width` / `height` を基準にした成果物画像の向きを表す。
- `backLocalUri`: 外側カメラで撮った元写真のアプリ内保存先。
- `frontLocalUri`: 内側カメラで撮った元写真のアプリ内保存先。背面カメラのみ撮影では `null`。
- `composedLocalUri`: アルバム一覧と詳細表示の主表示に使う成果物画像のアプリ内保存先。前後カメラ撮影では合成後写真、背面カメラのみ撮影では背面写真の保存先。
- `composedAssetId`: 成果物画像を端末の写真アプリへ保存したときの asset id。写真アプリ側の追跡に使う。
- `pattern`: 合成パターン。背面カメラのみ撮影では `null` を許容する。
- `composedWidth` / `composedHeight`: 成果物画像の出力サイズ。
- `frontImageFocusX` / `frontImageFocusY` / `frontImageScale`: 内側写真のどの位置を合成先の基準位置に合わせるかを、0〜1の座標と拡大率で保存する。背面カメラのみ撮影では `null`。

この方式にすると、以下を安定して実現できます。

- 一覧には成果物画像だけを表示する。
- 詳細では元の外側写真と内側写真も表示する。
- 前後写真がワンセットであることを確実に扱う。
- 合成パターンの選択結果を保存する。
- 撮影モードと出力向きを保存する。
- 将来の顔検出では、デフォルト値 `0.5 / 0.5 / 1.0` を顔位置と拡大率で置き換え、既存の合成処理へ渡す。
- 将来的に再合成やAI自動レイアウトへ拡張しやすい。

## DBなし設計について

写真ファイル名やメタデータだけで復元する設計も検討可能です。

例:

```text
LCR_20260506_143522_<pairId>_outer.jpg
LCR_20260506_143522_<pairId>_inner.jpg
LCR_20260506_143522_<pairId>_composite.jpg
```

メタデータ例:

```text
app_id: LifeCubeRequiem
schema_version: 1
pair_id: <uuid>
role: outer | inner | composite
captured_at: 2026-05-06T14:35:22+09:00
composition: diagonal_soft
```

ただし、DBなしを主軸にすると以下のリスクがあります。

- OSや写真アプリ側でメタデータの扱いが揃わない。
- ユーザーが写真を移動、編集、削除した場合にセット復元が難しくなる。
- 合成パターンの選択結果を安全に保存しにくい。
- アルバム一覧の高速表示や日付グルーピングが面倒になる。

そのため、MVP では以下の組み合わせを基本方針にします。

```text
主: アプリ内ローカルDB
副: ファイル名に pairId / role を入れる
補助: 可能ならメタデータにも同じ情報を入れる
```

## 写真アプリ保存とアプリ内保存

どちらも物理的には端末内に保存されますが、保存される領域と見え方が異なります。

アプリ内保存は、LifeCube アプリ専用の保存領域に置く方式です。通常の写真アプリには見えませんが、LifeCube のアルバムでは安定して参照できます。

端末の写真アプリ保存は、iOS の写真アプリや Android のフォト/ギャラリーから見える場所に保存する方式です。ユーザーの写真資産として扱いやすい一方、ユーザーが写真アプリ側で削除・編集でき、OS差も出やすくなります。

推奨する考え方:

- LifeCube 内アルバム用には、前後カメラ撮影では外側写真、内側写真、合成後写真の3枚をアプリ内保存領域に保存する。
- 背面カメラのみ撮影では、背面写真1枚を LifeCube アルバム用の成果物として保存する。
- ユーザーにとっての成果物として、前後カメラ撮影では合成後写真、背面カメラのみ撮影では背面写真を端末の写真アプリにも保存する。
- LifeCube 固有のセット関係や合成設定は、アプリ内DBで管理する。
- アルバム一覧は、SQLite の `createdAt` と `composedLocalUri` を使って表示する。
- 成果物画像は、縦向きでは `1080 x 1920` の9:16、横向きでは `1920 x 1080` の16:9を基本にする。
- 将来的には、カメラが返す画像サイズ、元写真のアスペクト比、必要な共有先に応じて、合成画像の出力サイズと比率をさらに調整できる設計にする。
- DBが壊れたり消えたりした場合の補助として、将来的にはファイル名やメタデータにも pairId を残す。
- アプリ内で写真セットを削除する場合は、DBの `deletedAt` を設定し、アプリ内保存の3枚をまとめて実ファイル削除する。
- 端末の写真アプリ側の削除は、OS確認ダイアログが絡むためMVP初期では行わない。
- アルバム一覧は合成後写真が存在する写真セットだけを表示する。
- 外側写真または内側写真だけが欠けた場合でも、合成後写真が存在すれば一覧には表示する。
- 元写真が欠けている場合、オリジナル表示では欠けている写真を表示できない状態として扱う。

現在のアプリ内保存先:

```text
FileSystem.documentDirectory/lifecube/photo-sets/{photoSetId}/back.jpg
FileSystem.documentDirectory/lifecube/photo-sets/{photoSetId}/front.jpg
FileSystem.documentDirectory/lifecube/photo-sets/{photoSetId}/composed.png
```

背面カメラのみ撮影では `front.jpg` を作らず、成果物画像として `composed.png` に背面写真を保存します。

端末写真アプリへの保存:

```text
成果物画像の composed.png のみ MediaLibrary.createAssetAsync() で保存する。
返ってきた asset.id を composedAssetId としてDBに保存する。
```

## 実機確認の優先順

1. iOS 実機で「シャッター」音声検知が継続動作するか。
2. Android 実機で「シャッター」音声検知が継続動作するか。
3. 外側カメラ撮影後、内側カメラへ切り替えて実用的な速度で撮れるか。
4. 撮影後の合成画像生成が端末性能的に許容範囲か。
5. 合成後写真が端末の写真アプリへ保存されるか。
6. 外側、内側、合成後の3画像を1セットとしてローカルDBに保存し、アルバムに出せるか。

## 初期実装の判断

最初の意味ある実装では、以下を優先します。

- カメラ起動をデフォルト画面にする。
- 音声検知撮影を残す。
- 外側から内側への連続撮影を安定させる。
- 撮影後は円形くりぬき合成を表示する。
- `expo-sqlite` のローカルDBで写真セットを管理する。
- 前後カメラ撮影では、アプリ内保存領域に外側、内側、合成後の3枚を保存する。
- 背面カメラのみ撮影では、背面写真1枚を LifeCube アルバムと端末の写真アプリの両方に保存する。
- 端末の写真アプリには成果物画像だけを保存する。
- アルバム一覧には成果物画像だけを表示する。

DBなし復元やAIによる最適合成は、MVP の初期範囲には入れません。

カメラ解像度や元写真比率を保った高画質出力は、MVP初期では扱わず将来検討とします。
