# 開発原則

## 基本原則

- モバイルアプリを第一に考えます。Web プレビューは、明示的にプロダクト対象へ昇格しない限り開発確認用です。
- Expo / React Native の標準的な作法を優先し、独自基盤を増やしすぎないようにします。
- TypeScript の strict 設定を維持し、重要なデータ構造は明示的に型で表現します。
- 変更は小さく、レビューしやすい単位に分けます。
- 既存のユーザー作業を壊さず、関係のないファイルを書き換えません。
- 意味のある設計判断は、決まったタイミングでドキュメントへ反映します。

## AI支援開発

AI エージェントには、広い範囲の作業を任せる想定です。

- 実装
- リファクタリング
- テスト
- ドキュメント更新
- アーキテクチャ提案
- レビューとリスク洗い出し

ただし、標準化する範囲はまだ確定していません。アーキテクチャ、永続化、バックエンド、ビルド設定、UI方針に関わる変更では、AI エージェントは前提を明示してください。

## 音声入力への対応

開発指示には音声入力が多く使われます。

AI エージェントは以下のように対応します。

- 文脈から明らかな音声認識ミスは補完します。
- 表現が揺れていても、ユーザーの意図が明確なら作業を進めます。
- 実装内容が分岐する曖昧さがある場合だけ、簡潔に質問します。
- 軽微な言い間違いや誤変換だけで作業を止めません。

## 環境と秘密情報

- 環境名は Expo / EAS 標準に合わせて `development` / `preview` / `production` に統一します。
- TestFlight は `preview` 環境の iOS 配布手段として扱い、独立した環境名にはしません。
- ローカル開発の環境値は `.env.local` を使い、Git 管理しません。
- `EXPO_PUBLIC_*` はアプリに埋め込まれ、ユーザーから見える前提で扱います。
- API secret、トークン、秘密鍵、管理者用URLなどの秘密情報を `EXPO_PUBLIC_*` やアプリバンドルに含めません。
- Expo projectId、bundle identifier、EAS profile、EAS channel、submit 設定を変更する場合は、影響範囲を明示してから変更します。

## ドキュメント運用

- `DOCS/` は現役の開発に使う文書として保ち、古い記録置き場にしません。
- 決定済みの内容は、該当する分野の文書へ移します。
- 未解決の論点は `open-questions.md` に移します。
- プロンプト雛形は、実際に AI ツールへ貼りやすい形で保ちます。
- 重複や探しにくさが出てきたら、ドキュメント構成を再整理します。

## ドキュメントに残す情報

チャットでは、開発中の疑問として一般的な基礎知識を確認することがあります。ただし、その場限りの説明をすべて README や `DOCS/` に反映すると、ドキュメントが肥大化して実務で読みにくくなります。

ドキュメントに残すもの:

- このプロジェクトで採用した技術判断
- 開発チームが継続的に守る運用ルール
- AI エージェントに毎回参照させたい制約
- アーキテクチャ、UI、ビルド、デプロイに関するプロジェクト固有の方針
- 未決定だが今後の判断に影響する論点

原則として残さないもの:

- 一般的な技術用語の説明
- チャット内で解決した基礎知識の Q&A
- 一度理解すれば開発規約として参照する必要がない説明
- 公式ドキュメントを読めば足りる汎用的な説明
